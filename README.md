## 案例：AR 眼镜多屏办公软件（代码不公开）

让 AR 眼镜接管电脑桌面：戴上眼镜，桌面变成眼前的两三块屏，转头就能在屏幕之间切换。

**真正的难点不是 3D，是「像一块真屏」。** 黑边、画面漂移、帧率掉到 30——任何一条都会让人当场弃用，而背后是虚拟屏驱动、显示拓扑、头部追踪、GPU 拷贝几条链路必须同时正确。

我在这里做的几个判断：

- **推倒重写。** 原型能跑，但要长期维护和发安装包，所以从脚本语言重写成 C#
- **零拷贝。** 桌面复制纹理在同设备直接渲染，GPU 不经内存；只有跨显卡才退回内存中转
- **消漂移。** 把每 0.5 秒内低于阈值的净转动当作漂移吸收掉，而不是让画面一直往一边走
- **把「能不能测」当功能做。** 31 项无设备单元测试、模拟电脑、发布前关卡脚本，让每次改动都能在没接眼镜的情况下先验证一遍

从 v1.0 迭代到 v1.0.8，多轮实机验证，稳定 60 帧。安装包在干净机器上完整自测过：装驱动 → 开双屏 → 覆盖升级 → 运行中卸载 → 显示恢复、驱动和文件全部清干净。

> 这个产品有单独的归属和知识产权安排，所以这里只讲做法和判断，不放代码。

## 我怎么做事

- **先想清楚给谁用**，再动手写第一行代码
- **能点开比能跑通更重要**：每个想法最后都要变成一个能直接发给别人的链接
- **限制要写出来**：数据是虚构的、没有后端、没有账号体系——这些会写在 README 里，而不是藏起来
- **别用「能跑」当验收标准**：帧率、边界情况、干净机器上的安装卸载，才是用户真正会遇到的地方
